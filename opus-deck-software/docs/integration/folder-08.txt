1. WHAT I BUILT
===============
folder-08 is the adversarial security gate: a pure-function ruleset of seven
vulnerability detectors (SEC-001..SEC-007), a multi-auditor scan engine that
deduplicates per (ruleId, path, line) while keeping the first detector's
attribution and capping at three hits per rule per file, and a bounded
remediation loop that emits `security-remediation` tasks on the shared bus,
re-scans only the patched (file, rule) pair, and escalates anything still
unresolved after two rounds to the leader's review queue. Low/medium findings
never block the gate: they pass through as advisories. Everything is
deterministic — same artifacts and auditors always produce byte-identical
reports — because rule ids, finding ids, task ids and escalation ids are all
derived from content, never from a counter or a clock (the clock is injected).
Zero runtime dependencies; `zod` was permitted but deliberately not used (see
§8.9). Builds under `tsc --strict` plus `noUncheckedIndexedAccess`,
`exactOptionalPropertyTypes`, `noUnusedLocals`, `noUnusedParameters` and
`noImplicitReturns`, with 145 passing tests across 6 test files.

interface Rule {
  readonly id: RuleId;                                  // `SEC-${string}`, e.g. 'SEC-004'
  readonly title: string;
  readonly severity: Severity;                          // 'critical'|'high'|'medium'|'low'
  readonly detectors: readonly string[];                // auditor ids, or 'any'
  readonly test: (line: string) => boolean;             // PURE, non-global regex only
  readonly fileTest?: (fileContent: string) => boolean; // PURE, whole file
  readonly patchStrategy?: PatchStrategy;               // 'escape'|'env-var'|'https'|'crypto-random'
  readonly locateFile?: (fileContent: string) => number[]; // additive extension, see §8.1
  readonly guidance: string;
}

4. EXPECTS FROM OTHERS
======================
UNKNOWN FOLDER NUMBER — see §8.2. folder-08 is forbidden from importing
across folder boundaries, so the owning folder numbers of these three
collaborators are not discoverable from inside folder-08. The integrator must
map each interface below to the folder that actually owns it and write a thin
adapter. Only the three shapes below are required; anything else those folders
expose is ignored by folder-08.

4.1 FROM the task-bus / worker-pool folder — OWNER UNKNOWN
----------------------------------------------------------
Stubbed against `TaskBus` in src/types.ts, implemented in src/stubs.ts
(`createStubTaskBus`). folder-08 uses it for exactly two things:
  a) `enqueue(RemediationTask) -> EnqueueReceipt`. A rejected task
     (`accepted === false`) escalates with reason `task-rejected` and consumes
     no further rounds.
  b) `awaitSettlement(receipt) -> BusTaskOutcome` (OPTIONAL). When absent,
     folder-08 re-scans immediately after enqueue and treats everything as
     unfixed. When present it MUST resolve only after the worker has finished
     writing the file, otherwise the verification scan reads stale bytes.
REQUIREMENT ON THE BUS: it must preserve `RemediationTask` objects verbatim
(the worker applies `patchStrategy`/`suggestion`/`targetPath`/`targetLine`).

4.2 FROM the workspace / COMMONS-IO folder — OWNER UNKNOWN
-----------------------------------------------------------
Stubbed against `ArtifactStore` in src/types.ts, implemented in src/stubs.ts
(`createStubArtifactStore`). folder-08 calls `read(path)` for ONLY the paths it
just asked to have patched, at most once per (path, rule) per round. The store
MUST return the current on-disk bytes, and MUST throw CommonsError (or any
Error) for an unknown path — a throw is escalated as `rescan-unavailable`,
never fatal.

4.3 FROM the leader / review-queue folder — OWNER UNKNOWN
----------------------------------------------------------
Stubbed against `EscalationQueue` in src/types.ts, implemented in
src/stubs.ts (`createStubEscalationQueue`). folder-08 calls `push(Escalation)`.
The queue is OPTIONAL: escalations are always returned in
`RemediationResult.escalations` even when no queue is wired. A rejected push
promise is swallowed on purpose and does not fail the audit.

4.4 FROM the orchestrator (not a stub — caller-supplied data)
--------------------------------------------------------------
`ModelRef[]` for the auditor roster, `Artifact[]` harvested from
COMMONS/WORKSPACE, and (optionally) a `now()` clock. Nothing else is imported.

5. PROVIDES TO OTHERS
=====================
5.1 THE GATE ITSELF — for the orchestrator / lead folder
    `scanAll(artifacts, auditors)` is the blocking decision input.
    Use `report.findings` + `gateBlocked(findings)` to decide whether the crew's
    build may proceed. Write `findings` to COMMONS/DELTA and `bySeverity` to
    COMMONS/STATE/digest.md.
5.2 REMEDIATION TASKS — for the task-bus / worker-pool folder
    `remediateFindings(...)` emits `kind: 'security-remediation'` tasks. The
    worker pool picks them up like any other task; dispatch on `kind`, order by
    `priority` (0 = critical) then `round`.
5.3 ESCALATIONS — for the leader / review-queue folder
    `kind: 'security-escalation'` entries with a machine-readable `reason`
    (see 3.6) so the leader can triage without re-reading the evidence.
5.4 THE RULESET — for anyone extending the gate
    Import `RULES`, `Rule`, `RULE_IDS` to add rules or narrow `detectors` per
    auditor model. New ids MUST continue at `SEC-008` and MUST NOT renumber
    SEC-001..007.
5.5 `escapeHtml` — for the worker models applying an `escape` patch. Reusing
    folder-08's definition guarantees the fix matches what the auditor reasoned
    about; a divergent re-implementation silently defeats the gate.
5.6 `findingId` — for the Compactor and for anyone merging findings across runs
    or across folders. It is a pure function of (ruleId, path, line), so the
    same defect always carries the same id without coordination.
5.7 NOTHING ELSE. folder-08 writes no files, reads no files, and performs no
    network or process-spawning I/O of its own. Every side effect goes through
    the three interfaces in §4.

6. CONFIG
=========
There are NO environment variables and NO configuration files. folder-08 reads
no `process.env`, no CLI flags and no config file. All behaviour is passed per
call through `ScanOptions` / `RemediationOptions` / `RemediationDeps`, so two
gates can run side by side with different rulesets.

The only "keys" folder-08 owns are string constants on the public surface:

| key / constant                   | type                | default      | purpose |
|----------------------------------|---------------------|--------------|---------|
| MAX_HITS_PER_RULE_PER_FILE       | 3                   | 3            | hard per-file per-rule cap; overridable downward via ScanOptions, clamped to [1,50] |

8. INTEGRATION NOTES
====================
8.1 `Rule.locateFile` is an additive extension I added. The briefed
    `fileTest` returns only a boolean and therefore cannot say WHERE it
    matched. `locateFile(fileContent) => number[]` returns 1-based lines for
    that attribution. Where a `fileTest` rule has no `locateFile`, the finding
    is reported at line 1 with `evidence: '[file-level match]'` — this is
    covered by a test, not an accident. Both shipped `fileTest` rules (SEC-004
    PEM keys, SEC-007 split comparisons) do provide `locateFile`.
8.2 FOLDER NUMBERING IS UNRESOLVED for the three interfaces in §4. I could not
    discover the owning folder numbers: no cross-folder imports are permitted
    and the other folders are invisible from here. Default assumption if the
    integrator has no better information: the task bus / worker pool and the
    artifact store live in the same folder as the crew orchestration, and the
    escalation queue is owned by the leader/planner folder. Verify before
    wiring. This is the single largest open item in this delivery.
8.3 RESOLUTION SEMANTICS. A finding is `resolved` iff re-scanning its file for
    its rule yields ZERO hits. It is NOT "the hit on line N is gone", because
    patching shifts line numbers and per-line matching would report false
    successes. Consequently a file with two hits on one line keeps that finding
    open; a worker that moves the defect to a different line does not fool the
    gate.
8.4 CRITICAL/HIGH WITHOUT A STRATEGY ARE ESCALATED, NOT IGNORED. SEC-001,
    SEC-003 and SEC-007 have no `patchStrategy`, so `remediateFindings`
    escalates them immediately with `reason: 'no-patch-strategy'` and
    `rounds: 0` — no task, no round spent. They are deliberately NOT
    advisories: an `eval()` must never pass the gate silently.
8.5 `unresolved` MEANS "still a blocking defect". It contains every unresolved
    critical/high input finding, including those escalated for a missing
    strategy and those whose task was rejected/failed. Use
    `gateBlocked(result.unresolved)` as the gate verdict.
8.6 ALL RULES DEFAULT TO `detectors: ['any']`, so every auditor applies the
    whole ruleset. Auditor ids are assigned at runtime by the orchestrator and
    are unknowable at build time; hard-coding ids here would silently disable
    rules. To give each auditor its own subset, spread `RULES` and narrow
    `detectors`, then pass the array as `ScanOptions.rules` (tested).
8.7 ATTRIBUTION AND THE THREE-HIT CAP INTERACT. Dedup keeps the FIRST
    auditor's id; later auditors only raise `auditorCount`. Once a (rule, path)
    pair reaches the cap, further hits for that pair are dropped entirely and
    are NOT counted as corroboration. `ScanReport.corroborated` is therefore a
    lower bound on true agreement.
8.8 AUDIT-ONLY, NO WRITES. folder-08 never modifies an artifact. Remediating is
    a bus task; `stubPatchers` in src/stubs.ts are deliberately naive one-line
    fixers that exist only to prove the loop converges in tests. Do not ship
    them as a fix engine.
8.9 `zod` IS NOT USED. The brief permits zod as the only runtime dependency;
    folder-08 takes zero runtime dependencies instead, because validation here
    is six field checks and an offline integrator should be able to build and
    test without a registry. Nothing in §3 requires zod.
8.10 FALSE-POSITIVE POSTURE IS DELIBERATELY ADVERSARIAL — the gate over-reports
    rather than under-reports, because a finding costs one worker round while a
    miss costs a breach. Known looser edges, all test-pinned: SEC-002 flags
    `el.innerHTML = render(x)` (any non-literal right-hand side); SEC-003 flags
    any line containing a SQL verb plus concatenation plus a quote/context;
    SEC-004 flags secret-shaped names anywhere on a line (including
    `secretKeeper = "..."`); SEC-005 flags every non-loopback http:// including
    internal networks. Comment-only lines are excluded from every rule, which is
    the single biggest noise reducer.
8.11 EVIDENCE IS TRUNCATED at 240 chars and whitespace-collapsed. Long minified
    or generated files should be excluded via `ScanOptions.excludePaths` rather
    than trusted.
8.12 `ModelRef.role`, `ModelRef.name` and `ModelRef.provider` are accepted but
    unused by folder-08; only `id` matters. `ModelRef` is accepted as a bare
    string in every function that takes auditors, which keeps call sites short.
8.13 The stubs in src/stubs.ts throw CommonsError themselves (E_INVALID_ARTIFACT,
    E_ARTIFACT_NOT_FOUND). When replacing them with real adapters, preserve that
    behaviour: the remediation loop relies on a throwing store read to escalate
    `rescan-unavailable` instead of crashing the audit.
8.14 Tests live in `test/` and compile to `dist/test/`. `npm test` runs
    `pretest` (a full rebuild) first, so a stale `dist/` can never mask a
    compile error.

9. DO NOT CHANGE
================
9.1 The `Rule.test` / `Rule.fileTest` purity contract. They MUST stay pure
    (no state, no clock, no I/O) and MUST NOT be written with a `/g` or `/y`
    flag used through `.test()`/`.exec()` — `lastIndex` would make the second
    auditor disagree with the first. Non-global regexes only.
9.2 Rule ids SEC-001..SEC-007, their severities and their declaration order.
    Ids are already persisted to COMMONS and to bus payloads; renumbering
    invalidates history. New rules start at SEC-008 and go at the end.
9.3 The dedupe key `(ruleId, path, line)` and first-detector attribution.
    Changing either changes what "two models caught the same bug" means, which
    is the gate's core signal.
9.4 The three-hits-per-rule-per-file cap. Without it one bad generated file can
    flood the bus and starve the crew.
9.5 The two-round ceiling on remediation and the escalation-after-exhaustion
    behaviour. It is the bound that stops a patch/re-scan war.
9.6 Resolution = zero remaining hits for (file, rule) after re-scan. See §8.3.
9.7 `findingId` = `FND-<12 hex>` over (ruleId, path, line). Any other derivation
    breaks cross-run dedupe in COMMONS and between folders.
9.8 `CommonsError` shape and `folder: 'folder-08'`, and the rule that folder-08
    throws nothing else. Consumers filter on `folder` and `code`.
9.9 The three interfaces in §4.5. Adapters are welcome; changing the shapes is
    not, because folder-08's verification loop depends on their exact timing
    semantics (see §4.1b).
9.10 `RemediationTask.kind === 'security-remediation'` and
    `Escalation.kind === 'security-escalation'`. The worker pool and the leader
    dispatch on these strings.
